## 已確認根因 RC-POSITION-01

可信但尚未完成的使用者尋位目標，與當前原生位置缺少分別保存的來源／有效期資訊。

| 因果節點 | 證據／來源 | 判定 |
| --- | --- | --- |
| 可信按鍵產生 T=2811.002824 | U-C01、I-P01／04；`src-v2/adapters/player-controls.ts:434` | 目標及一次 userRevision 正確 |
| 尚無進度，網站 readyState=0、currentTime=0 | U-C04；`player-controls.ts:138` 原生觀察及 `:188` 目標更新 | observed target 變 0、seekRevision 更新、userRevision 不變；觀察本身符合原契約 |
| 建立 trusted-player-play 意圖 | `src-v2/application/recovery-controller.ts:406`、`:426` 讀值 | 非 stall 路徑用 `player.currentTime()`，沒有可信未完成目標查詢 |
| 保存恢復位置 | `recovery-controller.ts:450` | 0 為有限合法值，因此保存 0；不能以「0 無效」修正 |
| 錯值進入 reload／restore | `recovery-controller.ts:493`、`:542` | 所有權檢查可防止過期操作，無法還原已遺失的 T |

最早的資訊缺口在原生重設後：原控制快照只剩目前觀察值，沒有獨立可信未完成目標。最早明確違反整合需求的狀態，是新 Recovery token 的 `savedPositionSec=0`。

固定序列為健康樣本→暫停至少 30 秒→可信 seek T→尚無合格進度→原生失效歸零→可信播放→4 秒後一次 reload。I-P01 的 1／2 倍均期待 2811.002824、實際 0；I-P04 的 A=2000→B=2811.002824 也保存 0。這是同一缺陷的最新目標變體。

正常對照：

- I-P02：無原生歸零，保存 2811.002824，1／2 倍皆通過。
- I-P03：使用者真正 seek 0，保存 0，1／2 倍皆通過。
- I-P05：A 已完成並有進度，後來新意圖保存當前 2100，沒有永久黏住 A。
- I-P06：新媒體／內容週期撤銷舊所有者；未知來源改至 400 不偽造使用者修訂，也不回寫舊目標。

## 救援與自然起因的結論邊界

I-R01 保存兩條現有路徑的差異。自有 stall reload 經空核心與網站初始化 seek 時，取消舊位置還原，rate／play 仍受所有權限制；trusted-player-play 在初始化 seeking 下以 seek-interrupted 結束。兩者由 `recovery-controller.ts:215`、`:347`、`:602` 等既有規則控制，測試均通過。**不把政策差異本身列為第二個已確認缺陷**。後續若要改初始化政策，須另有要求與失敗契約。

U-R04／07／08、I-R02 保障新 seek／pause／rate、reset、資格撤銷及晚到 Promise 不被舊動作覆蓋。U-R09／12 保障 15 秒終止、breaker 與最多兩次 reload，沒有證據支持延長期限或重設額度。

原自然停滯的請求等待→網站取消／重試→Auto 表示變化→媒體失效因果鏈仍未定位。這輪 Auto 2 倍局部媒體資料有進度，沒有位置缺陷的完整現場序列；網路窗口無效，不能把網站取消、CDN 回應或 Auto 切換指認為根因。

## 後續修復規格，尚未實作

唯一新增權威狀態仍放在 **PlayerControlObserver**。不要在 Recovery、Monitor、Runtime 或儲存元件建立另一份可獨立延壽的最後使用者目標。`PlayerControlSnapshot.targetSec` 保持目前觀察值語意。

建議最小內部介面為 Observer 經 PlayerAdapter 提供只讀目標證明取得／驗證能力，接入 RecoveryPlayerPort；不新增全域或 UI API。可用 `captureResumeTarget()`／`resumeTargetValid(proof)`，或等價的不可變證明＋驗證回呼。證明至少包含：

- 有限 `targetSec`，明確允許 0。
- Observer 分配的 goal ID／revision、媒體 ID、內容 generation／epoch 或同等 lifecycle key。
- 可信來源類別、pending／completed／revoked 狀態與操作身分。
- 同媒體／同核心及前後位置證據；不得輸出播放器物件、URL 或憑證。

這是設計，當前產品沒有上述介面；每項先補新增單元失敗契約再實作。

| 狀態／事件 | 規則 | 契約 |
| --- | --- | --- |
| 可信鍵盤／指標 seek 完成派送 | 取得實際有限目標才建立 pending，不從座標估算；同事件只建一次 | U-C01／02，加指標目標單元 |
| A 後可信 B | B 取代 A；B=0 同樣有效；舊證明永久失效 | I-P03／04 |
| 未完成且原生失效變 0 | 只有可歸因的同所有者失效才保留 pending；不能把所有 readyState=0 的 0 都視作本案 | U-C04、I-P01 |
| 未知位置變動、媒體／內容替換、控制失效 | 保守撤銷；不能只憑 userRevision 未變保留；reset／dispose 清除 | I-P06、U-C05／07 |
| 目標附近非 seeking 的連續合格進度 | 標記完成，後續新意圖用目前位置；完成狀態只歸 Observer，純比較可共用 | I-P05、U-P01／02 |
| 後續可信播放 | 驗證是同一 pending seek 的播放延續後交接；不能因 play 自身修訂變動誤殺，也不能把任意操作當延續 | 新增播放交接單元，I-P01／03 |
| 新 seek／pause／rate、drag 或生命週期撤銷 | 按操作類型撤銷／取代；舊 token 每個副作用提交點繼續檢查 | U-R04／07／08、I-R02 |

pending 只在同媒體／內容與可證明的未完成操作期間有效；完成、替代、撤銷即結束。不得延長 15／30／15 秒、固定保留最後 N 秒目標或無限跨核心保存。若新增時間到期政策，須另列需求／單元邊界，不可暗改長暫停行為。

Recovery 建立意圖時，先取得候選目標證明與一次位置／速率讀值；所有可能同步重入的讀取完成後，重新驗證目前生命周期、所有者、資格、額度及目標證明，再提交 token。沒有有效證明就維持目前有限原生位置邏輯；真正 0 不 fallback。reload／seek／setRate／play 前後與 Promise 尾端沿用現有檢查，另驗證證明未被新操作撤銷；不得用事前快照替代。

精確原生失效歸零的歸因仍需在修復前明定正反單元：同核心失效、未知 SDK seek 0、已完成進度後歸零、新媒體與可信零。若可觀察資料無法區分，不可宣稱任意 0 都可安全復原；應縮小允許保留證明的條件並列明限制。
