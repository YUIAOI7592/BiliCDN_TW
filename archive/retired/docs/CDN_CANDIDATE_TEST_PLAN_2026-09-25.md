# 新增 B 站 CDN 節點的驗證方案（2026-09-25）

> **狀態：已撤銷，不再作為新增節點的執行計畫。** 本文件僅保留當時的測試設計供歷史參考。已完成的 Node 初篩與內建瀏覽器播放觀察，及目前「只記錄、不新增 Catalog」的決定，見[測試結果](CDN_TEST_RESULTS_2026-09-25.md)。下方的待測狀態描述是撰寫本草案時的狀態。

> **文件定位：2026-09-25 歷史草案。** 下列步驟與待測表格不列入目前待辦；現行版本、Catalog 邊界與文件分類見[文件索引](../../../docs/INDEX.md)。

## 目的與結論等級

本方案評價[公開專案調查](CDN_OPEN_SOURCE_SURVEY_2026-09-25.md)列出的候選 Host，回答三個不同問題：它是否能讀取**當次、同一 representation** 的媒體、在台灣使用者的 Chrome 中是否比原生路線更穩、是否值得加入 v2 的內建 Catalog。公開清單和單次測速都只能決定測試次序，不能作為上線證據。

每個 Host 最後標記為「不相容」「證據不足」「可做受控試用」或「可提議納入 Catalog」。這是測試結論，不直接改變正式版的選線。

| 批次 | 待測 Host | 比較基線 |
| --- | --- | --- |
| 第一批 | `cn-hk-eq-01-03.bilivideo.com` | 同一 playurl 的原生 signed Native Host，及一個目前可用的 Catalog Host |
| 第二批 | `upos-sz-mirror08c.bilivideo.com`、`upos-sz-mirrorhwo1.bilivideo.com` | 同上；逐個評價，不合併成「深圳節點」 |
| 後續 | `upos-sz-mirrorawsov.bilivideo.com`、`upos-sz-mirrorcoso1.bilivideo.com` | 前兩批顯示需要更多選擇時再測 |

`upos-hz-mirrorakam.akamaized.net` 只可作 API 當次給出的 **exact Native URL** 對照，不得替換 Host 生成 Catalog URL。對其他地區、營運商或時段不得外推「最快」結論。

## 先建立安全的測試入口

目前正式版只會對 `TRUSTED_CATALOG` 生成目標 URL；上述新增 Host 不在其中。因此要測它們，先在**不發布的本地測試版本**設置固定的實驗 Host 清單，並透過既有 URL 解析、限制檢查和 `SignedRouteVault` 取得當次媒體。實驗清單不得接受任意輸入或遠端更新，不把候選寫進正式版 Catalog；不在 DevTools、檔案或命令列手工複製 signed URL。測試入口只在當前影片／當前 epoch 存活，切片、畫質、音訊軌、路由 epoch 一變就銷毀 URL 參照並取消探測。

動到執行邏輯前，依 `tests-v2/` 的 domain／controller／adapter 契約測試重現並守住下列行為：

1. 只從已解析、合法的 bilivideo 媒體 URL 換**固定允許的 Host**，保留路徑、查詢和 representation；只在當次授權範圍內使用。Akamai 仍只允許 exact Native。
2. 黑名單、停用、固定路線與原生／Catalog 限制都作用於實驗路線；停用時停止 script rewrite 與主動測試，不取消網站自身請求。
3. video／audio 分開計數與判定；舊 generation 的非同步結果不得更新狀態。測試不透過健康探索改變目前 Host，路線變更仍只由 `RouteCoordinator` 處理。
4. 只持久化有界的 Host 級摘要。不得保存或顯示 signed URL、path、query、token、Cookie、IP、影片識別碼或 player/core 物件。

## 第一關：正確性與相容性

在台灣的 Chrome＋Tampermonkey、實際登入／畫質條件下，選兩部可正常播放的影片：一部熱門、一部冷門；至少一個常用畫質，有高碼率觀看需求時另補一個高碼率 representation。每部都檢查 video 和 audio。每次比較只使用**同一部影片、同一畫質、同一 codec、同一 track 與同一有效 epoch**，原生 Host 作同場對照。

探測只在頁面可見、未 seek／恢復／停用、進度穩定至少 20 秒且可播放緩衝至少 30 秒時執行。順序量測，任一時間只對一個目標發請求；每輪最多原生 Host 加兩個候選。用頁面原生 `fetch` 發單一 `Range` GET，`credentials: 'omit'`、`cache: 'no-store'`、`redirect: 'error'`，拒絕 opaque 或跨 Host 回應。每次讀取最多 64 KiB、3 秒逾時，並且必須得到直接 HTTPS `206` 與完整要求的位元組。若回應有可讀的 `Content-Range`，核對起訖位移；瀏覽器未對腳本暴露該 header 時記為「無法由腳本讀取」，另在 Chrome Network 人工核對，不把缺少 header 當作失敗。

對每個 video／audio 資源測開頭和一個**已確認仍在該資源長度內**的後段位移。無法確認合法後段位移就標記「未驗後段」，不得以開頭成功推論整個檔案可用。相同 Host 如出現 `403`、`451`、`959`、`416`、轉址、短回應、逾時或 CORS／網路失敗，記錄類別並用新 epoch 重試一次；原生對照若同時失敗，該組不計入 Host 相容性判斷。不得用 `no-cors` 或單純連通視為成功。

每個候選的主動探測額外流量上限：單次 64 KiB，完整一輪最多 3 個 Host；單場累計最多 4 MiB、兩輪間隔至少 15 分鐘。緩衝跌破 30 秒、頁面隱藏、seek、generation 改變或使用者停用時立即取消**測試請求**。這些限制只約束額外探測流量，正常播放另行計量。

## 第二關：速度與實際播放

只有通過第一關的 Host 才進入此關。對同一 video representation，以原生／候選輪換順序量測各 3 次，分布在至少兩個不同時段；每次最多讀 512 KiB、3 秒，仍維持一次一個、緩衝門檻與 4 MiB 單場上限。記錄每次 TTFB、讀完時間、實收位元組與保守吞吐量；計算保守吞吐量時沿用現行 `MeasurementController` 的 0.7 折減，並比較較低分位而非最高 Mbps。測試順序交錯或反轉，減少快取和時段偏差。音訊仍以正確性和播放穩定為主要門檻，不以音訊樣本 Mbps 排名。

再以**實際播放**驗證，而非只看探測結果：原生與候選各跑至少 2 部影片 × 2 個時段，每組約 5 分鐘，成對交換先後順序。每組保持相同畫質、codec、播放速率和網路環境；記錄首幀時間、每 10 分鐘換算的卡頓次數／秒數、seek 後恢復、video／audio 錯誤，以及 Chrome Network 實際媒體請求 Host。候選的播放路線必須由受控測試版本經合法路由邊界選定，不能以測速 Host 冒充實際播放 Host。若網路大幅波動、播放器自動改畫質或原生對照不可用，該組重做。測試時段和網路類型可記錄，精確 IP、HAR 與 URL 不記錄。

## 決策門檻

| 判定 | 必要證據 |
| --- | --- |
| 不相容 | 在原生對照成功的相同資源上，候選於新 epoch 重試後仍出現簽名拒絕、非直接 `206`、內容不足或不正確 Range；只對該 Host／資源類型下結論，並查明是否為特定影片或地區。 |
| 證據不足 | 只有開頭 64 KiB、單一影片／時段、未確認實際 Host、無合法後段位移，或原生對照同時失敗。不可加入正式 Catalog。 |
| 可做受控試用 | 兩部影片的 video／audio 開頭及後段均通過，沒有重現的拒絕／轉址／錯誤，兩時段保守吞吐量的低分位達播放需求的 1.35 倍，且成對播放沒有新增卡頓、起播或音訊退化。僅代表已測環境。 |
| 可提議納入 Catalog | 受控試用通過，且至少一個實際問題有可重現改善，例如原生在成對播放中卡頓而候選較少；完整自動化測試、Chrome/Tampermonkey 驗收和安全差異掃描均通過。若原生一路無卡頓，不能宣稱候選改善了卡頓。 |

單次失敗先保留原因和對照，不用總平均掩蓋特定 video、audio 或後段失敗。新增 Host 若只在一個台灣 ISP 通過，結論限定該 ISP；正式版是否預設可用需另評估覆蓋範圍。跨地區節點不得因本地平均 Mbps 較高就覆蓋既有 Native 備援。
