# BiliCDN_TW v2.2.11：剩餘 TODO 優化研究

日期：2026-11-07（Asia/Taipei）。程式基準為乾淨 main `060b79ffba2c257a73e8d3a5257291d028a7097a`，現行發行版 v2.2.11。本次依使用者「研究 TODO 如何優化」的新目標執行，只研究、離線推演與保存文件。工作狀態由 [TODO](../../../docs/TODO.md) 維護；原安裝結果仍以 [TEST_REPORT](../../../docs/TEST_REPORT.md) 為準。

## 研究結論

六類 TODO 均有後續處理方式，但不能全部視為待修缺陷。

1. **先做小範圍結構整理：** 退役沒有產品讀者的最後成功主機投影，再於 UI 邊界合併同一同步批次的路線通知。保留功能事件、設定立即抑制及命令後的新快照。
2. **提前重試先查適用性，再查效益：** 正數 timeout 可參與起播，卻仍不能參與提前重試。近期自然正數請求不能用來證明提前重試有機會工作；不宜先放寬 1.35 或交接門檻。
3. **熔斷不重跑已通過的二十分鐘：** 既有受控四段降級與安裝普通接線已成立。剩餘工作是原生故障／降級接縫、真正共享鎖及 GM 通知的證據；它們各有不同限制。
4. **舊卡頓與香港供片先建立可反駁的歸因條件：** 失敗請求、實際影片主機、取消來源及恢復資格必須配對；流暢、音訊成功或排名標記均不能單獨解答根因。
5. **條件式缺口改成精確分支清單：** 普通自然起播已有 v2.2.10 R4 證據，不能籠統稱為「起播從未驗證」。P01／P02 的等待者／重新準備交錯則仍保持封存範圍。
6. **數學模型優先補 VBR、量測語意及外推界線：** 平均碼率、畫質或 FPS 單獨不足以推算片段期限；網站 ABR、解碼服務與未選來源仍是未識別變數。

本研究沒有確認新的現行產品故障，也沒有證明新版熔斷參數、選路或提前重試已達實機最優。以下方案是後續實作與驗證建議，不是本次實作授權。

## 一、延後程式整理

### TD01：退役最後成功主機索引

**現況證據。** [RouteCoordinator](../../../src-v2/application/route-coordinator.ts) 的 `#lastSuccess` 在 reset 清除、成功時由 `#latest` 保存參照；`latestVideoHost()` 核對成功、匹配、六十秒及回應主機。全域引用搜尋確認只有 [介面宣告](../../../src-v2/application/route-contracts.ts)、實作及 [adapters 套件](../../../tests-v2/suites/adapters.ts) 兩個讀取斷言，沒有產品呼叫者。這是最多 video／audio／unknown 三類的參照索引，不是大量資料複製或診斷歷程。

**建議。** 後續先保留原案例名稱，將 abort 案改以真正保留的成功健康樣本驗證「取消不抹除合法學習」；generation reset 案以目前請求、回應歸因與容量均不跨生命週期驗證。跨片合法主機學習本來可保留，不能錯改成 reset 清除 EvidenceStore。完成反向案例後，刪除方法、介面、Map 及維護點。

**可減少的負擔。** 一份只供測試讀取的索引、每次成功的 Map 更新及讀取方法；不宣稱播放速度提高。風險低至中等，影響內部介面及原測試的表達方式，沒有儲存或使用者操作變更。

**驗證。** 成功後 abort、失敗、歸因不符、影音分離、過期及換片；保留合法成功樣本，舊內容不回填目前畫面。型別、相關傳輸與完整案例對照通過後才退役。

### TD02：只合併 UI 刷新通知

**現況證據。** RouteCoordinator 的 `requestStarted()` 同步依序發出 request-started 與 attribution-changed；[ControlReadModel](../../../src-v2/ui/control-read-model.ts) 將 settings／monitor／routes 通知直接轉交；[ControlCenter](../../../src-v2/ui/control-center.ts) 每次通知立即 snapshot／refresh。[Runtime](../../../src-v2/application/runtime-controller.ts) 另直接接收影片備援恢復事件，必須維持同步順序。

**建議。** 在讀模型的 UI 訂閱邊界，將 routes／monitor 的相鄰通知以一個私有 microtask 合併，執行時才讀新快照。settings 的立即狀態通知及命令完成刷新保留原時機；不能把所有事件整批改為非同步。排隊工作綁定訂閱／視圖版本，關閉、換頁與重開不更新舊畫面。同步顯式刷新若已處理該批狀態，應使舊排隊工作失效，避免再刷新一次。

HTML 的 microtask 可在目前同步執行結束後處理，適合合併這裡的相鄰通知；但不同非同步回呼不保證合成一次，不應宣稱「每秒只刷新一次」。這是本研究的適用性推論，標準沒有替本產品保證狀態等價。[HTML 微任務規格](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#microtask-queuing)

**風險與驗證。** 中等風險，改變 UI 通知時機。覆蓋通知重入、settings 鎖等待立即抑制、保存失敗／遠端更新、命令完成讀新模型、初次三頁／詳細文字按需、關閉重開及失效視圖；另斷言 Runtime 影片恢復事件仍立即且只交接一次，音訊不交接。不新增輪詢或平行事件匯流排。

### TD03：保留抑制能力，先縮小內部責任

**現況證據。** `suppressEarlyRetryEvidence()` 只有 [up141-retry-transport](../../../tests-v2/regressions/up141-retry-transport.ts) 建立／驗證受控成功抑制。它使用最多 32 個 ID、參考計數及冪等釋放；成功帳本另有 32 筆、六十秒與精確普通傳輸資格。抑制只阻止提前重試替代帳本，不阻止一般 EvidenceStore 寫入，更不是完整安裝故障隔離工具。

**建議。** 不為消除測試方法而移除受控證據保護。若後續帳本修改頻繁，可將接納、過期、唯一請求及抑制租期收回同一個由 Routes 私有持有的既有 routing 助手；先維持對外窄行為，避免順便更改時間與資格。不建立全域註冊器、完整 Store 注入或新的公開測試後門。沒有其他改動需求時維持現狀，優先度低於 TD01／TD02。

**驗證。** 重疊租期、重複釋放、容量上限、先前成功立即排除、晚到成功仍受抑制、生命週期清理、同內容兩筆實傳及舊授權拒絕。不能以共用長期速度樣本替代短期重試授權帳本；整合主要減少所有權跳轉，沒有已量得的效能收益。

## 二、熔斷驗證與工具方法

### TD04：補接縫，不重跑已通過路徑

[v2.2.11 R2](../../../docs/TEST_REPORT.md#v2211-r2-受控熔斷與安裝接線2026-11-06) 已有 45 案受控矩陣、四段各至少五分鐘的實時 L4→L0，以及安裝版影音各 42 筆完整普通接線。剩餘證據拆成三項：

| 剩餘項 | 可以怎麼補 | 不能用來代替的材料 |
| --- | --- | --- |
| 原生失敗→接納→共享升級 | 未來合法來源隔離中，以真實適配器與獨立儲存提供原生可控制結果，核對一次終止、失敗分類與保存 | Node 合成事件不能算原生 XHR；安裝成功接線不能算失敗接線 |
| 安裝版隔離到期→五分鐘→保存降級 | 若未來有合格資料與安全隔離條件，只補一段共享提交接縫；不必為證明時間再次跑四段 | 不改正式 GM 的 L／U、不縮期限、不以成功樣本回灌製造前提 |
| 真正 GM 跨分頁同步 | 只有另獲改變單分頁限制的授權才可實測；目前維持雙 Store 契約層級 | 同頁兩個記憶體 Store 不能稱為兩個 Tampermonkey 分頁 |

目前沒有可安全隔離全部正式熔斷寫入的既有產品開關。不能拿 TD03 的局部抑制直接在安裝版注入失敗；那會留下人工故障控制資料，違反保留學習的前提。若工具不能合法載入隔離來源，停止該層，不使用本機服務或外部瀏覽器繞過。

[Storage 實作](../../../src-v2/platform/storage.ts) 的 sharedLockAvailable 檢查 API，真正共同性仍依平台／儲存分區。Web Locks 以共享儲存範圍協調，不能跨 origin 或隔離的使用者代理宣稱共鎖；現行 metadata 的匹配頁皆為 https 的 www.bilibili.com，但這不足以證明 Tampermonkey 實機協作已測。[Web Locks 規格](https://www.w3.org/TR/web-locks/#lock-scope) [Tampermonkey 儲存與通知](https://www.tampermonkey.net/documentation.php?locale=en#api:GM_addValueChangeListener)

**政策建議維持現狀。** 不重開「同波只升一次」方案；逐筆不同失敗升級、10／30／120／360 分鐘與 W／G／C=5／2／1 分鐘沿用已確認選擇。參數是否更好，需故障恢復分布與流量間隔證據，不能由四段通過推定最優。

### TD05：先修取回方法，再增加實測項目

R2 首次取回約 43.982 秒，後續最大間隔約 38.641 秒；同時序號完整、零溢位，支持普通接線配對，卻沒有證明十秒落地已校準。R3／R4 的問題也顯示，延後讀取與缺失事件必須分開。

後續私有驗收方法採下列規則：

- 工具往返晚到時，下一次排程跳到真正未來的十秒節點；不快速補讀過期時槽來冒充十秒節奏。
- 來源序號與本機保存確認分開；保存失敗不能推進已確認游標，重讀按 ID 冪等合併。固定容量外另記遺失數，連續的保留序號不能掩蓋溢位。
- 來源自行固定邏輯截止；最後窗內值、實際截止回呼、邊界讀值及取回時間分欄。晚讀不能延長，也不能用截止後媒體狀態補成窗內狀態。
- 先以獨立哨兵及小範圍作用域驗證續讀，哨兵不計產品事件；可執行來源位置、欄位及本體身分凍結後才開始產品窗口。
- 只有浮點表示等價可用縮放 epsilon；不能將真正超期改成數值誤差。取證缺口只限制依賴它的案例。

新私有原型五案已核對上述核心資料規則。這些是下一輪工具設計，尚未修寫歷史採樣器或證明 IAB 往返上限；也不新增正式 scripts/iab、產品歷程或診斷功能。休眠／長排程中斷撤銷相關窗口，不能拼接；單調時鐘與牆鐘分工仍須保持。[High Resolution Time 時鐘定義](https://www.w3.org/TR/2026/WD-hr-time-3-20260225/#clocks)

## 三、提前重試的適用性與效益

### TD06：先盤點到達資格的漏斗

[XhrEarlyRetry.register](../../../src-v2/adapters/xhr-early-retry.ts) 仍要求非同步影片 Catalog GET、單一閉合 Range、m4s 及原生 timeout=0，之後才接受可信 progress 與直接 206。網站寫 timeout 的修訂、固定主機、控制狀態、兩筆實傳替代資格等仍會再排除。

v2.2.10 R4 的自然影片入口／原生送出為 13,000 ms；v2.2.11 R2 範例為 10,000 ms。這些例子不證明所有請求都是正數，但確實**不能進入目前提前重試跟蹤**。R2 原本 earlyRetry=false，更不能由該輪推算開啟時的實際機會。v2.2.7 舊九十秒全為正數的調查只代表當時指定窗口，不外推全站。

未來先用外部有界去敏觀察，分層統計：媒體輸入→影片 Catalog／Range→timeout=0→可信進度／206→控制狀態→合格替代→純判定→許可→網站認領→實際供片。每層附分母、重疊拒絕與未知，不能將無機會算作效用失敗，也不能從少量例子推定效用通過。

**建議決策。** 目前保留正數 timeout 的既定排除，不擅改網站值。若之後證明主要工作負載適用率接近零，先決定是否接受擴大控制範圍，再另起安全與相容方案；不可只刪 timeout 判斷就宣稱安全擴充。保留現行範圍時，文件與目前狀態應準確表達適用限制，避免把「開啟」誤當「所有慢請求都會介入」。不以新增診斷計數器作本次解法。

### TD07：用明確效益與成本取代保證式想像

[純判定](../../../src-v2/domain/early-retry.ts) 的核心為：

```text
替代總時間 = 2 + TTFB秒 + 完整重送bytes × 8 / (本文Mbps × 1,000,000)
替代總時間 ≤ 0.8 × 可播放緩衝秒
原路剩餘時間 − 替代總時間 ≥ 1秒
```

正數大小、有限速度及有效計時使替代總時間大於兩秒，因此 **緩衝≤2.5秒必定不符合**。這是既定兩秒預算與 80% 條件的直接推論，未增加新門檻。7,680 組只變更大小、進度、緩衝、目前速度、替代速度及等待的格點亦符合；不能將 1,076／7,680 解讀成現場觸發率。

同一份決策前資料下，原路可能繼續慢、立即恢復，或替代路線突然變慢。新模型分別令原路完成 18／0.2／18 秒、替代含交接完成 2.3／2.3／25 秒，四秒緩衝的停頓收益為 +14／0／−7 秒；後兩者另有重下載成本。這證明有限過去不足以保證每次介入受益，不能藉調一個閾值同時滿足所有可能未來。

現有六情境工具仍有效 FAIL，保留原輸入、退出碼與門檻；其中「全部慢場景都改善」與現行保守抑制有取捨，「正常突發恢復不介入」也不是純歷史條件能保證。後續可新增補充評估，不改舊 FAIL：

1. 分開接線正確、決策前估計、網站交接成功及實際播放效益；actualRetry 的定義明列是否已含 timeout／重送等待，不能重複加或漏加兩秒。
2. 在相同內容、表示軌跡及外部服務曲線上配對繼續／重試，輸出停頓差、完成差、額外 bytes、重載及無必要介入。未執行的另一條路線標未知，不填零或失敗。
3. 保留持續慢、突發恢復、替代變慢及無交接等反向場景；以時間／內容分組保留資料，預測只使用當時已完成證據，避免用未來資訊選參數。
4. 任何放寬、預設或新效用門檻都需另立政策。現階段沒有支持更改 1.35、兩筆六十秒或正數 timeout 資格的實機數據。

## 四、歷史根因與香港供片

### TD08：建立問題別的最小歸因鏈

| 問題 | 現有證據能說什麼 | 後續最小證據／改進 |
| --- | --- | --- |
| CC39-R01／N05 | 移除 Evolved 後一窗未再現；取消發起者未知 | 同請求的自然取消、當時選擇／操作與媒體事件；建立取消是使用者、網站 ABR、腳本還是未知的可反駁分支。未知不能硬分類 |
| CC39-R02／HK04 | 合法備援的恢復資格已修；舊 emptied／loadstart 起因未明 | 分別核對影片失敗、合法備援提交、恢復資格、實際 SDK 派送與媒體替換；不將後發事件直接當先前取消原因 |
| CC39-R03／香港 | 曾有影片 timeout；修後隔離時由其他 CDN 供片 | 指定內容／Range、video、實際回應主機與結果配對。音訊 206、固定偏好或計畫主機不能算香港影片成功 |
| CC39-R04／playerReady | 移除 Evolved 後未再觀察，因果未知且獨立重測已取消 | 維持歷史未解；未來若相同錯誤自然再現才保存最小去敏來源與時間，不恢復獨立矩陣 |

建議把「無法識別的舊根因」與「現在可獨立保護的產品契約」分開：後者已有取消不熔斷、舊路線不奪權、影片備援恢復、音訊隔離等測試，可以維護；前者不能用合成成功結案。現行 403／404／410 是資源／主機配對限制，timeout／network／body／5xx 才依資格影響主機熔斷；不因香港名稱或單內容缺檔改成全域禁止。

優先補離線事件交錯與分類反向案例，再判斷是否值得另立有界現場研究。沒有可辨識的自然事件與允許的觀察條件時，保留未知比追加任意重載或增加探測更合理。本次不安排停用其他腳本、固定 CDN、重測取消議題或新香港窗口。

## 六、數學模型與研究路線

### TD10：先校準可觀測層，不要求還原全部網站私有 ABR

保留既有 [Auto 與 VBR 研究](AUTO_CDN_MATHEMATICAL_MODEL_v2.2.8_2026-11-04.md) 的數字、207 筆逐時預測、探索性 stage4 限制與停止決策。本次新目標只重新啟動離線研究，不恢復 Auto 窗口、ABBA 或網站來源執行。

模型分三層：

| 層 | 必要參數 | 能做的分析 |
| --- | --- | --- |
| 請求交付 | bytes、同語意等待／本文耗時、主機、媒體、併發、樣本年齡 | 分大小／年齡／timingBasis 核對完成誤差及低估，不把 goodput 當物理容量 |
| 播放資源 | 各表示片段大小及媒體時長、連續影音緩衝、實際倍率、表示軌跡 | 檢查片段是否趕上期限、緩衝洞、重下載及交接成本 |
| 網站與裝置 | Auto 有效設定、決策歷史、codec／FPS、解碼服務能力 | 未識別時列外生軌跡或敏感度，不補成現場真值、不讓畫質或 smooth 旗標代替解碼能力 |

固定表示的離散模型可寫為：

```text
T_k = 等待_k + S_k × 8 / C_k
可用期限_k = B_k / r_k
停頓_k = max(0, T_k − 可用期限_k)
B_(k+1) = max(0, B_k − r_k × T_k) + Δ_k
```

S 用 bytes、C 用 bit/s、B／Δ 用媒體秒、r 為實際倍率。此式假設整段完成才增加可用緩衝，沒有並行 append 或解碼瓶頸；真實漸進交付需分開建模。影音各自計算，播放受必要連續區間限制，不能把分離區間或不相容表示緩衝相加。

新反例固定四段各四秒、總量 12 MB、8 Mbps、每段等待 0.1 秒、初始四秒媒體緩衝：VBR 大小 8／1／1／2 MB，均勻大小 3／3／3／3 MB。平均影片碼率同為 6 Mbps；一倍時連 25% 裕度後仍低於 8 Mbps，但第一個大段仍造成 4.1 秒模型停頓，均勻情境為零。這不是說現行產品應額外下載索引，而是平均需求不能保證每段期限。

FPS 應與 codec、解析度一同描述表示與裝置負荷；已含 FPS 影響的壓縮 bitrate 不再乘 FPS。若要研究解碼，可檢查條件 `倍率×宣告FPS ≤ 可持續解碼FPS`，但右側目前未知，不能由宣告值或能力旗標倒推；必要條件也不保證播放順暢。本次沒有恢復掉幀收集。

BOLA 使用緩衝與畫質效用處理 ABR 取捨；Pensieve 亦以網路與內容條件評估閉環。可參考它們建立外生表示軌跡與反例，但本產品只選路，不應直接移植成網站畫質控制或新的遠端學習服務。[BOLA 原論文](https://arxiv.org/abs/1601.06748) [Pensieve 原論文](https://people.csail.mit.edu/hongzi/content/publications/Pensieve-Sigcomm17.pdf)

### TD11：完成估計與因果效益分開校準

先用已合法取得的去敏數字建立固定資料字典及時間切分：當次預測只取送出前已完成、相同 timingBasis／媒體／主機且支持範圍內的樣本。小請求不能直接外推大 VBR 段；舊樣本沒有 timingBasis 時只能作相容容量或探索分析，不冒充新版完成比較資格。

同時列 MAE、低估耗時、期限誤判、大小／年齡分組及資料量；對相關連續請求不使用獨立樣本信賴區間。參數比較保留快慢 EWMA、七折、25%、1.35 及交接預算的正式基線，候選只在私有離線資料上做敏感度；不得因某格點勝出直接換產品參數。

另一主機在同時刻的結果通常未被觀察。既有偏好選路資料也沒有隨機選擇機率與完整支持範圍，不能套逆機率公式補造換站因果收益；只有明列假設下的上下界或合成比較。離線 replay／counterfactual 方法本身也依賴收集策略與可觀測支持，不能消除未選動作缺值。[Unbiased Offline Evaluation 原論文](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/published-3.pdf)

建議先把「保持原路」與「等待／換路」成本列齊，再決定是否值得另外授權現場配對；不要把還原全部 ABR 或解碼能力當成修小範圍計時／結構問題的前置門檻。沒有替代容量證據時，產品健康主機穩定沿用政策保持。
